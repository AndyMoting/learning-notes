# 03-用例设计方法-下

> 课时：100 min | 难度：★★★★

## 学习目标

- 掌握因果图的构建方法，能将自然语言需求转化为可执行的图形化因果逻辑
- 掌握正交表（L9/L12/L16）的查表设计法，能针对多因子多水平场景压缩用例数量
- 掌握场景法中的基本流与备选流建模，能对业务流程图进行测试路径覆盖
- 能根据需求特征选择最合适的用例设计方法，并说明选择依据

## 核心概念

### 因果图（Cause-Effect Graph）

**定义**：以图形方式表达输入条件（因）与输出结果（果）之间的逻辑关系，通过中间节点表达约束关系，最终转换为判定表以生成测试用例。

**图形符号**：

```
恒等：   C ─────→ E          C=1则E=1；C=0则E=0

非：     C ──▷──→ E          C=1则E=0；C=0则E=1

或：    C1 ╲
             ╲▷──→ E          C1或C2任一为1则E=1
        C2 ╱

与：    C1 ╲
             ╳──→ E          C1和C2同时为1则E=1
        C2 ╱

互斥：    C1 ──|
                |──→ E        C1、C2至多一个为1
             C2 ──|

包含：    C1 ──|
                |──→ E        C1、C2不能同时为0（至少一个为1）
             C2 ──|

唯一：    C1 ──|
                |──→ E        C1、C2有且仅有一个为1
             C2 ──|

要求：    C1 ──|
                |──→ E        C1为1时C2也必须为1
             C2 ──|

屏蔽：    C1 ─────→ E         （C1为1则强制E=1，忽略其他约束）
```

**设计步骤**：

1. 分析需求，识别所有"原因"（输入条件）和"结果"（输出/状态）
2. 用图形符号连接原因与结果，标注约束（互斥、包含、唯一、要求、屏蔽）
3. 将因果图转换为判定表（每个原因/中间节点为条件桩，每个结果为动作桩）
4. 根据判定表生成测试用例

**示例：文件上传功能判定**

需求：用户上传文件，要求文件格式为.jpg或.png，文件大小≤2MB。若格式不对且大小超限，优先提示格式错误。

```
原因：
  C1 = 文件格式为.jpg
  C2 = 文件格式为.png
  C3 = 文件格式为其他
  C4 = 文件大小≤2MB
  C5 = 文件大小>2MB

结果：
  E1 = 上传成功
  E2 = 提示"格式错误"
  E3 = 提示"文件过大"
  E4 = 提示"格式错误"（C3+C5同时满足时优先提示格式）

约束：
  C1、C2、C3 互斥（唯一一种格式）
  C4、C5 互斥
  优先约束：C3+C5 → E2优先于E3

因果图：
   C1 ──┐
        ├──[恒等]──→ E1
   C4 ──┘

   C2 ──┐
        ├──[恒等]──→ E1
   C4 ──┘

   C3 ──┐
        ├──[非]──→ E1
        └──[屏蔽]──→ E2（C3时抑制E1）

   C5 ──┘(C3未触发时)──→ E3
```

转换为判定表（合并）：

| 规则 | 1 | 2 | 3 | 4 |
|------|---|---|---|---|
| C1(.jpg) | T | F | F | F |
| C2(.png) | F | T | F | F |
| C3(其他) | F | F | T | T |
| C4(≤2MB) | T | T | T | F |
| C5(>2MB) | F | F | F | T |
| E1 上传成功 | √ | √ | | |
| E2 格式错误 | | | √ | √ |
| E3 文件过大 | | | | |

### 正交表（Orthogonal Array）

**定义**：从全排列组合（笛卡尔积）中按照正交性（均衡分散性、整齐可比性）选取代表性子集，使测试用例数量从 M^N 降至对数级，同时保证每对因子/水平至少组合一次。

**表示法**：L<sub>N</sub>(k<sup>m</sup>)
- N = 测试用例数
- k = 每因子水平数
- m = 因子数

**常用正交表**：

| 正交表 | 用例数 | 因子数 | 水平数 |
|--------|--------|--------|--------|
| L4(2^3) | 4 | 3 | 2 |
| L8(2^7) | 8 | 7 | 2 |
| L9(3^4) | 9 | 4 | 3 |
| L12(2^11) | 12 | 11 | 2 |
| L16(4^5) | 16 | 5 | 4 |
| L16(2^15) | 16 | 15 | 2 |

**L9(3^4) 正交表**：

| 用例\列 | A | B | C | D |
|---------|---|---|---|---|
| 1 | 1 | 1 | 1 | 1 |
| 2 | 1 | 2 | 2 | 2 |
| 3 | 1 | 3 | 3 | 3 |
| 4 | 2 | 1 | 2 | 3 |
| 5 | 2 | 2 | 3 | 1 |
| 6 | 2 | 3 | 1 | 2 |
| 7 | 3 | 1 | 3 | 2 |
| 8 | 3 | 2 | 1 | 3 |
| 9 | 3 | 3 | 2 | 1 |

**设计步骤**：

1. 识别所有因子（变量）及其水平（取值）
2. 根据因子数选正交表（因子数≤m，水平数≤k）
3. 将因子水平填入正交表对应列
4. 若因子数少于表列数，多余列可设为默认值或补虚拟因子
5. 若水平数不足（如二水平填三水平表），用重复法填充

**示例：测试用例设计工具配置文件（覆盖率策略）**

因子/水平表：

| 因子 | 水平1 | 水平2 | 水平3 |
|------|-------|-------|-------|
| A=操作系统 | Windows | macOS | Linux |
| B=浏览器 | Chrome | Firefox | Safari |
| C=分辨率 | 1920×1080 | 1366×768 | 375×812 |
| D=语言 | zh-CN | en-US | ja-JP |

因子数=4，水平数=3 → 选用 L9(3^4)

测试用例：

| 用例 | 操作系统 | 浏览器 | 分辨率 | 语言 |
|------|----------|--------|--------|------|
| TC1 | Windows | Chrome | 1920×1080 | zh-CN |
| TC2 | Windows | Firefox | 1366×768 | en-US |
| TC3 | Windows | Safari | 375×812 | ja-JP |
| TC4 | macOS | Chrome | 1366×768 | ja-JP |
| TC5 | macOS | Firefox | 375×812 | zh-CN |
| TC6 | macOS | Safari | 1920×1080 | en-US |
| TC7 | Linux | Chrome | 375×812 | en-US |
| TC8 | Linux | Firefox | 1920×1080 | ja-JP |
| TC9 | Linux | Safari | 1366×768 | zh-CN |

原需 3^4 = 81 条 → 正交表压缩至 9 条，覆盖率保证任意两个因子各水平组合至少出现一次。

### 场景法（Scenario-Based Testing）

**定义**：模拟用户实际使用场景，通过业务流程图（Flow Chart）或事件流图（Event Flow Diagram）识别测试路径，对每条路径设计测试用例。

**核心概念**：

```
                    ┌──────────────────────┐
                    │      场景开始         │
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │  基本流（Base Flow）  │
                    │  主成功路径，无异常   │
                    └──────────┬───────────┘
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
  ┌───────▼───────┐   ┌───────▼───────┐   ┌───────▼───────┐
  │  备选流A      │   │  备选流B      │   │  备选流C      │
  │  分支情况1    │   │  分支情况2    │   │  分支情况3    │
  └───────┬───────┘   └───────┬───────┘   └───────┬───────┘
          │                    │                    │
          └────────────────────┼────────────────────┘
                               │
                    ┌──────────▼───────────┐
                    │      场景结束         │
                    └──────────────────────┘
```

| 术语 | 说明 |
|------|------|
| 基本流（Base Flow） | 主成功路径，所有操作无任何异常 |
| 备选流（Alternative Flow） | 分支路径，含异常、取消、条件分支等 |
| 场景（Scene） | 基本流 + 0~N 条备选流的一次完整执行 |

**示例：ATM取款场景**

基本流：
1. 插入银行卡
2. 输入密码（正确）
3. 选择"取款"
4. 输入金额（≤余额，≤单笔限额）
5. 出钞
6. 退卡

备选流：
- B1：密码错误，允许重新输入（最多3次）
- B2：密码连续错误3次，吞卡
- B3：输入金额>余额，提示"余额不足"
- B4：输入金额>单笔限额，提示"超过单笔限额"
- B5：退卡超时未取，回收卡片
- B6：出钞异常，冲正交易

场景矩阵：

| 场景ID | 基本流 | 备选流 | 描述 |
|--------|--------|--------|------|
| S1 | ✓ | — | 正常取款成功 |
| S2 | ✓ | B1 | 密码错1次后正确，取款成功 |
| S3 | ✓ | B2 | 密码错3次，吞卡 |
| S4 | ✓ | B3 | 余额不足，取款失败 |
| S5 | ✓ | B4 | 超单笔限额，取款失败 |
| S6 | ✓ | B5 | 退卡超时，卡片回收 |
| S7 | ✓ | B6 | 出钞异常，交易冲正 |

### 方法选择策略

| 需求特征 | 推荐方法 | 理由 |
|----------|----------|------|
| 输入域有明确范围/类型 | 等价类 + 边界值 | 覆盖有效/无效输入，边界是缺陷高发区 |
| 多条件布尔组合 | 判定表 | 全量覆盖条件组合，无遗漏 |
| 条件间有复杂约束（互斥/依赖） | 因果图 → 判定表 | 图形化表达约束，再转表 |
| 多因子多水平，组合爆炸 | 正交表 | 指数级压缩用例数，保证两两覆盖 |
| 业务流程/用户操作路径 | 场景法 | 模拟真实用户路径，覆盖分支与异常 |
| 输入域无明确边界，依赖经验 | 错误推测法 | 基于经验枚举常见错误场景 |

**组合使用原则**：

```
需求文档
    │
    ▼
┌─────────────────────────────┐
│ 1. 识别输入域 → 等价类+边界值 │
│ 2. 识别条件组合 → 判定表/因果图│
│ 3. 识别业务流程 → 场景法      │
│ 4. 识别多因子 → 正交表        │
│ 5. 补充异常 → 错误推测法      │
└─────────────────────────────┘
    │
    ▼
最终测试用例集
```

## 动手实操

### 任务1：用因果图分析"自动售货机"需求

需求：售货机接受1元、5角硬币。按钮可选"可乐"、"雪碧"、"矿泉水"。规则：
- 可乐1.5元，雪碧1.5元，矿泉水1元
- 投币不足时显示"请继续投币"
- 投币足够时出货并找零
- 投币超过2元时显示"投币过多，请退币"

1. 识别原因与结果

```
原因：
  C1 = 选择可乐
  C2 = 选择雪碧
  C3 = 选择矿泉水
  C4 = 投币=1元
  C5 = 投币=1.5元
  C6 = 投币=2元
  C7 = 投币>2元

结果：
  E1 = 显示"请继续投币"
  E2 = 出货（可乐/雪碧/矿泉水）
  E3 = 找零
  E4 = 显示"投币过多，请退币"
```

2. 构建因果图（简化为判定表）

| 规则 | 1 | 2 | 3 | 4 | 5 | 6 |
|------|---|---|---|---|---|---|
| C1(可乐) | T | F | F | F | F | F |
| C2(雪碧) | F | T | F | F | F | F |
| C3(矿泉水) | F | F | T | F | F | F |
| C4(投币=1元) | F | F | T | F | F | F |
| C5(投币=1.5元) | T | T | F | F | F | F |
| C6(投币=2元) | F | F | F | T | F | F |
| C7(投币>2元) | F | F | F | F | T | F |
| E1 继续投币 | | | | | | √ |
| E2 出货 | √ | √ | √ | √ | | |
| E3 找零 | | | | √ | | |
| E4 投币过多 | | | | | √ | |

3. 编写Python验证脚本

```python
def vending_machine(drink: str, coin: float) -> dict:
    prices = {"可乐": 1.5, "雪碧": 1.5, "矿泉水": 1.0}
    if drink not in prices:
        return {"error": "无效选择"}
    if coin > 2.0:
        return {"message": "投币过多，请退币"}
    if coin < prices[drink]:
        return {"message": "请继续投币"}
    change = round(coin - prices[drink], 2)
    return {"drink": drink, "change": change}

# 因果图导出的测试用例
test_cases = [
    ("可乐", 1.5, {"drink": "可乐", "change": 0}),
    ("雪碧", 1.5, {"drink": "雪碧", "change": 0}),
    ("矿泉水", 1.0, {"drink": "矿泉水", "change": 0}),
    ("可乐", 2.0, {"drink": "可乐", "change": 0.5}),
    ("可乐", 3.0, {"message": "投币过多，请退币"}),
    ("可乐", 0.5, {"message": "请继续投币"}),
]

for drink, coin, expected in test_cases:
    result = vending_machine(drink, coin)
    status = "PASS" if result == expected else "FAIL"
    print(f"{drink} + {coin}元 → {result} [{status}]")
```

4. 运行验证

```bash
python test_vending_machine.py
```

## 常见坑

1. **因果图中遗漏中间节点** — 当原因与结果之间存在多步逻辑时，必须引入中间节点，否则约束关系无法正确表达。
2. **正交表因子水平数不匹配时强行填充** — 二水平因子填入三水平表时，应用"重复法"（如1,1,2），不可随意填3，否则破坏正交性。
3. **场景法中备选流未考虑循环** — 如"密码错误重试"是循环备选流，需设计"重试1次"、"重试2次"、"重试3次吞卡"三个场景。
4. **正交表忽略因子间交互作用** — 若已知某两个因子存在强交互（如浏览器×分辨率），应使用带交互作用的正交表或补充用例。
5. **因果图转判定表时遗漏约束** — 互斥、唯一、要求等约束必须在判定表中体现，否则会产生无效规则。
6. **场景法只测基本流** — 基本流仅覆盖主路径，备选流（异常分支）才是缺陷高发区，必须覆盖。
