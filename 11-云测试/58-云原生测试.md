# 58-云原生测试
> 课时：60 min | 难度：★★★★☆

## 学习目标
- 理解云原生架构的核心组件：容器、微服务、无服务器
- 掌握 Kubernetes 基础概念及其在测试环境中的应用
- 理解服务网格与契约测试在微服务测试中的价值
- 掌握混沌工程基本原则与工具
- 理解可观测性三支柱及其在测试中的作用

## 核心概念

### 云原生架构三要素

| 要素 | 说明 | 测试关注点 |
|------|------|-----------|
| 容器 | 轻量级进程隔离，一致性运行环境 | 镜像构建验证、容器网络测试 |
| 微服务 | 独立部署的小型服务单元 | 服务间通信、契约一致性 |
| 无服务器 | 事件驱动，按需执行 | 冷启动延迟、并发限制 |

### Kubernetes 核心对象

| 对象 | 说明 | 测试用途 |
|------|------|----------|
| Pod | 最小部署单元，包含一个或多个容器 | 测试执行单元 |
| Service | 稳定的网络端点，负载均衡到 Pod | 测试目标端点 |
| Deployment | 声明式管理 Pod 副本数 | 滚动更新测试 |
| ConfigMap/Secret | 配置与敏感数据管理 | 测试配置切换 |
| Namespace | 资源隔离 | 测试环境隔离 |

### 服务网格测试要点

- **流量管理**：金丝雀发布、蓝绿部署验证
- **故障注入**：模拟服务降级、超时
- **安全通信**：mTLS 验证
- **可观测性**：分布式追踪数据采集

### 可观测性三支柱

| 支柱 | 工具示例 | 测试用途 |
|------|----------|----------|
| 日志（Logs） | ELK Stack、Loki | 错误排查、测试执行记录 |
| 指标（Metrics） | Prometheus、Grafana | 性能基线、资源监控 |
| 追踪（Traces） | Jaeger、Zipkin | 分布式调用链分析 |

### 契约测试：Pact 实现

```python
# test_order_service_contract.py
import pytest
from pact import Consumer, Provider

@pytest.fixture
def pact():
    pact = Consumer('OrderService').has_pact_with(
        Provider('PaymentService'),
        pact_dir='./pacts',
        log_dir='./logs'
    )
    pact.start_service()
    yield pact
    pact.stop_service()

def test_create_payment(pact):
    """订单服务调用支付服务的契约验证"""
    expected = {
        'payment_id': 'pay_123456',
        'status': 'pending',
        'amount': 99.99,
        'currency': 'CNY'
    }

    (pact
     .given('a valid order exists')
     .upon_receiving('a request to create payment')
     .with_request('POST', '/api/v1/payments', body={
         'order_id': 'ord_789',
         'amount': 99.99,
         'currency': 'CNY'
     }, headers={'Content-Type': 'application/json'})
     .will_respond_with(201, body=expected))

    with pact:
        result = pact.u.create_payment(
            order_id='ord_789',
            amount=99.99,
            currency='CNY'
        )
        assert result['status'] == 'pending'
        assert result['payment_id'] == 'pay_123456'
```

## 常见坑

1. **Pod 未设置资源限制**：单个 Pod 耗尽节点资源，影响其他测试。解决方案：始终设置 requests/limits
2. **健康检查配置不当**：readinessProbe 初始延迟过短，导致服务未就绪就接收流量。解决方案：根据应用启动时间合理设置 initialDelaySeconds
3. **契约测试版本不匹配**：消费者与提供者使用不同版本契约。解决方案：使用 Pact Broker 统一管理契约版本
4. **混沌实验影响范围过大**：未限制实验范围，影响生产环境。解决方案：先在测试环境验证，设置精确的 target selector
5. **日志采集遗漏**：容器日志未集中采集，排查困难。解决方案：部署 Fluent Bit/Fluentd 统一采集到 ELK
