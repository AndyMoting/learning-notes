# 项目1-ShopTest全链路测试

> 覆盖模块：接口测试 + Web自动化 + 性能测试 + 安全测试 + DevOps
> 预计用时：8-10 小时
> 难度等级：中高

---

## 1. 项目概述

### 1.1 项目背景

ShopTest 为模拟电商平台，包含用户认证、商品浏览、购物车、订单管理等核心业务模块。本项目要求对该平台执行全链路测试，覆盖从接口到UI、从功能到非功能、从手工到自动化的完整测试流程。

### 1.2 项目目标

- 对 ShopTest 电商平台执行端到端测试
- 交付完整的测试报告、自动化脚本和 CI/CD 配置
- 建立可复用的测试框架与工程化实践

### 1.3 前置条件

| 类别 | 要求 |
|------|------|
| 编程语言 | Python 3.8+ / JavaScript（任选其一） |
| 测试工具 | Postman、Playwright、JMeter、ZAP |
| 平台环境 | ShopTest 服务已部署并运行（本地或测试环境） |
| 版本控制 | Git + GitHub 仓库 |
| 基础知识 | HTTP协议、REST API、测试用例设计方法 |

## 2. 任务分解

### 阶段1：接口测试（2小时）

#### 2.1.1 任务说明

使用 Postman 对 ShopTest 全部接口进行系统化测试，覆盖正向与反向场景，验证接口功能正确性、参数校验、鉴权机制及异常处理。

#### 2.1.2 具体要求

1. **创建测试集合（Collection）**
   - 按业务模块划分子集合：用户认证、商品管理、购物车、订单管理
   - 每个接口包含完整的请求配置（URL、Method、Headers、Body）

2. **编写测试用例**
   - 总计不少于 20 条测试用例
   - 正向用例：验证正常业务流程下的接口响应
   - 反向用例：验证参数缺失、类型错误、越权访问、Token过期等异常场景
   - 每条用例需包含明确的断言（状态码、响应体字段、响应时间）

3. **鉴权流程**
   - 实现完整的 Token 鉴权链路：登录获取 Token → 设置环境变量 → 业务接口携带 Token 访问
   - 验证 Token 失效后的响应行为

4. **导出配置**
   - 导出 Collection JSON（v2.1格式）
   - 导出 Environment JSON（包含 base_url、token、user_id 等变量）

#### 2.1.3 评分细则

| 评分项 | 分值 | 评分标准 |
|--------|------|----------|
| 用例覆盖率 | 8 | 覆盖全部核心接口，无遗漏；正向+反向比例合理（约6:4） |
| 断言完整性 | 7 | 每条用例包含状态码断言、关键字段断言、响应时间断言 |
| 鉴权实现 | 3 | Token自动获取与传递正确，失效场景覆盖 |
| 文档规范 | 2 | 用例命名清晰，描述完整，导出文件可直接执行 |

### 阶段2：UI 自动化（3小时）

#### 2.2.1 任务说明

使用 Playwright 编写端到端自动化测试脚本，覆盖用户核心业务流程，采用 Page Object 模式保证代码可维护性。

#### 2.2.2 具体要求

1. **测试场景（不少于10个）**
   - 用户注册流程
   - 用户登录/退出
   - 商品列表浏览与搜索
   - 商品详情页查看
   - 添加商品到购物车
   - 购物车商品数量修改
   - 购物车商品删除
   - 提交订单流程
   - 订单列表查询
   - 订单详情查看

2. **Page Object 模式**
   - 每个页面封装为独立类（LoginPage、ProductPage、CartPage、OrderPage）
   - 页面元素定位器集中管理
   - 页面操作方法与测试逻辑分离

3. **测试框架**
   - 使用 pytest 作为测试运行器
   - 配置 conftest.py 管理浏览器实例（fixture）
   - 支持 headless/headed 模式切换

4. **报告生成**
   - 集成 Allure 报告框架
   - 报告包含：用例标题、执行步骤、截图（失败时自动捕获）、执行时长

#### 2.2.3 评分细则

| 评分项 | 分值 | 评分标准 |
|--------|------|----------|
| 场景覆盖 | 8 | 10个核心场景全部覆盖，流程完整 |
| PO模式规范 | 7 | 页面类封装合理，定位器与逻辑分离，代码复用率高 |
| 代码质量 | 5 | 命名规范，结构清晰，异常处理完善，无硬编码等待 |
| 报告完整性 | 5 | Allure报告可正常生成，失败截图有效，步骤描述清晰 |

### 阶段3：性能测试（2小时）

#### 2.3.1 任务说明

使用 JMeter 对商品列表接口执行压力测试，验证系统在高并发场景下的性能表现，分析关键性能指标。

#### 2.3.2 具体要求

1. **测试脚本配置**
   - 线程组：100 并发用户，Ramp-up 30秒，持续运行5分钟
   - 请求：商品列表接口（GET /api/products）
   - 参数化：使用 CSV Data Set Config 实现搜索关键词参数化

2. **监听器配置**
   - View Results Tree（调试阶段使用）
   - Summary Report / Aggregate Report
   - Response Time Graph
   - 后端监听器（Backend Listener）对接 InfluxDB（可选）

3. **报告生成**
   - 使用 JMeter Dashboard Report 生成 HTML 报告
   - 报告包含：Samples、Average、Median、90%/95%/99% Line、Throughput、Error%

4. **性能分析**
   - 记录 TPS（每秒事务数）
   - 记录 P95 响应时间
   - 记录错误率
   - 判断是否满足性能基线（P95 < 500ms，错误率 < 0.1%）

#### 2.3.3 评分细则

| 评分项 | 分值 | 评分标准 |
|--------|------|----------|
| 脚本正确性 | 8 | 线程组配置准确，参数化实现，无逻辑错误 |
| 报告完整性 | 7 | Dashboard报告完整，关键指标齐全 |
| 指标分析 | 5 | TPS/P95/错误率数据记录准确，有明确结论 |

### 阶段4：安全测试（1小时）

#### 2.4.1 任务说明

使用 OWASP ZAP 对 ShopTest 平台执行自动化安全扫描，识别常见安全漏洞，输出安全报告。

#### 2.4.2 具体要求

1. **扫描配置**
   - 目标 URL：ShopTest 平台地址
   - 扫描类型：主动扫描（Active Scan）
   - 扫描策略：Standard，覆盖全部默认规则

2. **安全报告**
   - 按风险等级分类：High / Medium / Low / Informational
   - 每个风险项包含：漏洞名称、风险等级、URL、描述、修复建议
   - 重点关注：SQL注入、XSS、CSRF、敏感信息泄露、不安全的HTTP头

3. **修复建议**
   - 针对每个 High/Medium 风险项提供具体修复方案
   - 修复建议需具备可操作性

#### 2.4.3 评分细则

| 评分项 | 分值 | 评分标准 |
|--------|------|----------|
| 扫描完整性 | 6 | 主动扫描覆盖全部页面和接口，无遗漏 |
| 报告质量 | 6 | 风险分类清晰，描述准确，修复建议可操作 |
| 风险识别 | 3 | 能识别出至少3个有效安全风险（含至少1个High级别） |

---

### 阶段5：CI/CD 集成（1小时）

#### 2.5.1 任务说明

编写 GitHub Actions 工作流，实现代码提交后自动执行测试并上传报告。

#### 2.5.2 具体要求

1. **工作流配置**
   - 触发条件：push 到 main 分支 / pull_request 到 main 分支
   - 运行环境：ubuntu-latest
   - 语言环境：Python 3.10 / Node.js 18（根据自动化脚本语言选择）

2. **执行步骤**
   - Step 1：Checkout 代码
   - Step 2：安装依赖（pip install / npm install）
   - Step 3：代码检查（flake8 / eslint）
   - Step 4：执行接口测试（Postman via Newman）
   - Step 5：执行 UI 自动化测试（Playwright）
   - Step 6：上传测试报告（Allure Report 作为 Artifact）

3. **状态验证**
   - 工作流可手动触发（workflow_dispatch）
   - 任一步骤失败则标记工作流为失败
   - 报告文件正确上传至 Artifacts

#### 2.5.3 评分细则

| 评分项 | 分值 | 评分标准 |
|--------|------|----------|
| 流程完整性 | 6 | 触发条件、步骤顺序、依赖安装、测试执行、报告上传完整 |
| 可执行性 | 6 | 工作流可直接运行，无语法错误，步骤逻辑正确 |
| 健壮性 | 3 | 包含错误处理，失败时有明确提示，支持手动触发 |
