## 核心概念

### 服务器基础资源监控

**CPU 监控：**

```bash
# top：实时进程级资源使用
top -H  # 显示线程级 CPU 使用率

# 关键指标：
# %us：用户态 CPU（业务逻辑）
# %sy：内核态 CPU（系统调用/中断）
# %wa：I/O 等待（磁盘瓶颈）
# %id：空闲率
```

```bash
# vmstat：系统整体状态
vmstat 1 10  # 每秒采样，共 10 次

# 关键列：
# r：运行队列长度（> CPU 核心数说明 CPU 瓶颈）
# b：阻塞队列长度（I/O 等待的进程）
# si/so：swap 进出（> 0 说明内存不足）
# id：CPU 空闲百分比
```

**内存监控：**

```bash
free -h              # 查看内存使用
vmstat 1             # 关注 si/so（swap 使用）
cat /proc/meminfo    # 详细内存信息
```

**磁盘监控：**

```bash
iostat -x 1 10  # 每秒采样

# 关键指标：
# %util：磁盘利用率（接近 100% 为瓶颈）
# await：I/O 平均等待时间（ms）
# avgqu-sz：平均队列长度
```

**网络监控：**

```bash
netstat -an | grep ESTABLISHED | wc -l   # 当前连接数
netstat -s                                 # TCP 统计信息（重传率）
sar -n DEV 1 10                           # 网卡流量（bytes/s）
```

### APM 工具选型

| 工具 | 特点 | 适用场景 |
|------|------|----------|
| SkyWalking | 开源、Java 生态、探针自动注入 | 微服务架构全链路追踪 |
| Pinpoint | 开源、字节码注入、可视化强 | Java 应用 APM |
| Zabbix | 企业级监控、告警完善 | IT 基础设施监控 |
| Prometheus + Grafana | 时序数据库 + 可视化 | 云原生/容器化环境 |
| New Relic / Dynatrace | 商业产品、功能全面 | 企业级商业 APM |

**SkyWalking 核心概念：**
- Agent：随应用进程部署，无侵入采集 Trace/Metric
- OAP Server：聚合分析平台
- Web UI：展示链路拓扑、服务性能、慢请求
- Trace：完整请求链路，含各 Span 耗时

### JVM 监控与诊断

```bash
# jstat：JVM 运行时统计
jstat -gcutil <PID> 1000 10      # GC 每秒统计
# S0/S1：Survivor 区使用率
# E：Eden 区使用率
# O：老年代使用率
# M：元空间使用率
# YGC/YGCT：Young GC 次数和耗时
# FGC/FGCT：Full GC 次数和耗时

# jstack：线程栈分析
jstack <PID> > thread_dump.txt
# 重点查找：BLOCKED 状态线程、死锁（Found one Java-level deadlock）

# jmap：堆内存分析
jmap -heap <PID>               # 堆配置和当前使用
jmap -histo <PID> | head -20   # 对象实例数和内存占用 Top 20
jmap -dump:format=b,file=heap.bin <PID>  # 导出堆转储（MAT 分析）
```

**GC 日志分析：**

```bash
# JVM 启动参数：
-XX:+PrintGCDetails -XX:+PrintGCDateStamps
-Xloggc:/var/log/gc.log -XX:+UseGCLogFileRotation
-XX:NumberOfGCLogFiles=10 -XX:GCLogFileSize=100M
```

### 数据库慢查询分析

**MySQL 慢查询：**

```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒记录
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 查看慢查询配置
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';
```

```bash
# mysqldumpslow 分析
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
# -s t：按查询时间排序
# -t 10：显示前 10 条
```

**常见慢查询优化方向：**
- 索引缺失/失效（EXPLAIN 分析执行计划）
- 返回行数过多（分页/流式查询）
- 锁等待（查看 `SHOW ENGINE INNODB STATUS`）
- 子查询改写为 JOIN
- 大事务拆分为小事务

### 性能瓶颈识别方法论

**层进式诊断流程：**

```
1. 确认瓶颈所在层
   ├── 客户端层：压测工具本身是否饱和
   ├── 网络层：带宽/延迟/丢包率
   ├── 应用层：CPU/内存/JVM/线程池
   ├── 中间件层：连接池/消息队列/缓存命中率
   └── 数据库层：锁等待/慢查询/连接池耗尽

2. 逐层收集证据
   └── 监控数据 + 日志 + 线程堆栈 + GC 日志

3. 建立假设并验证
   └── 调整参数/优化代码/扩容 → 对比压测数据变化

4. 定位根因
   └── 资源不足 / 配置不当 / 代码缺陷 / 架构问题
```

### 性能调优常见方向

| 层面 | 问题现象 | 调优手段 |
|------|----------|----------|
| JVM | Full GC 频繁 | 增大堆内存、调整年轻代比例、切换 G1/ZGC |
| 线程池 | 请求排队拒绝 | 调整核心/最大线程数、队列容量 |
| 数据库 | RT 过高 | 索引优化、SQL 改写、读写分离、分库分表 |
| 缓存 | 缓存击穿/雪崩 | 布隆过滤器、随机过期时间、多级缓存 |
| 连接池 | 获取连接超时 | 增大连接数、设置合理的超时和回收策略 |

## 动手实操：性能问题诊断全流程

**场景：接口 P99 响应时间从 200ms 升至 3000ms**

**步骤 1：收集基础资源数据**

```bash
# CPU 使用率
top -H -p <PID> | head -20

# 系统资源
vmstat 1 5
iostat -x 1 5

# 网络连接
netstat -an | grep ESTABLISHED | wc -l
netstat -s | grep -i retrans
```

**步骤 2：JVM 诊断**

```bash
# GC 频率和耗时
jstat -gcutil <PID> 1000 20

# 线程状态分布
jstack <PID> | grep "java.lang.Thread.State" | sort | uniq -c

# 检测死锁
jstack <PID> | grep -A 10 "Found one Java-level deadlock"

# 导出堆快照
jmap -dump:live,format=b,file=/tmp/heap_$(date +%s).hprof <PID>
```

**步骤 3：应用日志分析**

```bash
# 查看错误日志
tail -f /var/log/app/application.log | grep -E "ERROR|WARN"

# 分析响应时间分布
grep "response_time" /var/log/access.log | awk '{print $NF}' | sort -n | \
  awk 'BEGIN{c=0} {a[c]=$1; c++} END{
    print "P50:", a[int(c*0.5)];
    print "P90:", a[int(c*0.9)];
    print "P95:", a[int(c*0.95)];
    print "P99:", a[int(c*0.99)];
  }'
```

**步骤 4：数据库诊断**

```sql
-- 当前活跃连接和等待
SHOW PROCESSLIST;
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';

-- 锁等待
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
SELECT * FROM information_schema.INNODB_LOCKS;

-- 慢查询 TOP 10
SELECT * FROM mysql.slow_log ORDER BY query_time DESC LIMIT 10;
```

**步骤 5：编写性能测试报告**

```markdown
# 性能测试报告

## 1. 测试概述
- 测试时间：2025-XX-XX
- 测试环境：4C8G × 3 节点
- 测试工具：JMeter 5.6.3 / Locust 2.x
- 测试目标：系统支持 1000 并发，P95 < 2s

## 2. 测试场景与结果

| 场景 | 并发数 | TPS | RT(Avg) | RT(P95) | RT(P99) | 错误率 |
|------|--------|-----|---------|---------|---------|--------|
| 登录接口 | 500 | 320 | 850ms | 1500ms | 2200ms | 0.02% |
| 订单查询 | 1000 | 580 | 1200ms | 2800ms | 4500ms | 0.15% |

## 3. 资源使用情况
- 应用节点 CPU：峰值 85%（3 节点）
- 数据库 CPU：峰值 92%（存在瓶颈）
- JVM Old Gen：峰值 95%，Full GC 12 次/小时
- 网络带宽：占用 60%

## 4. 瓶颈分析
1. 数据库 CPU 饱和：慢查询 `SELECT * FROM orders` 无索引
2. JVM Full GC 频繁：订单对象未释放，疑似内存泄漏
3. 订单接口错误率略高：数据库连接池偶尔耗尽

## 5. 优化建议
1. 为 orders 表 user_id 列添加索引（预估 RT 降低 60%）
2. 引入 Redis 缓存热点订单数据
3. 将 HikariCP 连接池从 20 扩容至 50
4. 排查订单对象引用未释放问题（MAT 分析 heap dump）
```

## 常见坑

- 只看 CPU 平均使用率：Java 应用可能单核 100%+ 其他核空闲，需要 `-H` 线程视图
- 忽略 GC 对响应时间的影响：Stop-The-World GC 会导致 P99 突刺
- 堆内存设得过大：堆越大 Full GC 越长，通常不超过 32GB（压缩指针限制）
- 只看慢查询不分析执行计划：`EXPLAIN` 才能确认是否走了正确索引
- 压测期间才开启监控：基线数据（正常负载下的指标）缺失导致无法对比
