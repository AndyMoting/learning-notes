## 第01课时：软件测试岗位调研对比表

### 知识点回顾

岗位调研需覆盖三个维度：岗位职责、技能要求、薪资水平。对比时应选取初级、中级、高级三个层级，以体现职业发展路径的差异。

### 参考答案：软件测试岗位三级对比表

| 对比维度 | 初级测试工程师（0-2年） | 中级测试工程师（2-5年） | 高级测试工程师/测试开发（5年+） |
|----------|------------------------|------------------------|--------------------------------|
| **岗位职责** | 执行手动测试用例；记录并跟踪Bug；编写测试报告；参与需求评审 | 设计测试用例；编写自动化测试脚本；分析测试结果；指导初级工程师 | 制定测试策略与规范；搭建自动化测试框架；性能/安全测试；测试团队管理 |
| **技能要求** | 熟悉测试基础理论（等价类、边界值）；掌握Bug管理工具（JIRA禅道）；了解SQL基础；熟悉Linux基本命令 | 掌握至少一门编程语言（Python/Java）；熟练使用接口测试工具（Postman）；熟悉CI/CD流程；具备数据库查询能力 | 精通自动化测试框架（Selenium/Playwright/JMeter）；具备性能测试调优能力；熟悉微服务架构测试；具备测试平台开发能力 |
| **薪资水平（参考）** | 6K-10K/月 | 12K-20K/月 | 20K-40K/月 |
| **典型证书** | ISTQB Foundation | ISTQB Advanced、软件评测师 | 无硬性要求，项目经验为主 |
| **核心差异点** | 执行层，侧重用例执行与Bug记录 | 设计层，侧重用例设计与自动化实现 | 策略层，侧重测试体系搭建与技术攻关 |

## 第02课时：用户名字段测试用例设计

### 知识点回顾

用户名通常有以下约束规则（以常见系统为例）：
- 长度：6-20个字符
- 字符类型：字母（大小写）、数字、下划线，不允许特殊字符
- 首字符：必须为字母
- 唯一性：不可与已有用户名重复

采用**等价类划分法**与**边界值分析法**组合设计。

### 参考答案：用户名字段测试用例（10条）

| 用例编号 | 输入数据 | 预期结果 | 测试类型 | 覆盖的等价类/边界 |

| 等价类类型 | 描述 | 代表值 |
|-----------|------|--------|
| 有效等价类 | 字母开头，6-20字符，仅含字母/数字/下划线 | `alice_01` |
| 无效等价类-长度不足 | 长度 < 6 | `abc` |
| 无效等价类-长度超出 | 长度 > 20 | `a_very_long_username_over_20_chars` |
| 无效等价类-首字符非法 | 首字符非字母 | `123abc` |
| 无效等价类-含非法字符 | 含特殊字符或空格 | `abc@123` |
| 无效等价类-空值 | 空字符串 | （空） |
| 无效等价类-重复 | 已存在的用户名 | `alice_01`（已注册） |

### 边界值分析明细

| 边界点 | 测试值 | 预期结果 |
|--------|--------|----------|
| 长度=5（下边界-1） | `abcde` | 失败 |
| 长度=6（下边界） | `abcdef` | 成功 |
| 长度=7（下边界+1） | `abcdefg` | 成功 |
| 长度=19（上边界-1） | `abcdefghijklmnopqrs`（19位） | 成功 |
| 长度=20（上边界） | `abcdefghijklmnopqrst`（20位） | 成功 |
| 长度=21（上边界+1） | `abcdefghijklmnopqrstu`（21位） | 失败 |

## 第03课时：正交法——ATM取款场景

### 知识点回顾

正交实验设计法利用正交表（如L9(3^4)）从全量组合中选取代表性组合，以最少用例覆盖最大组合范围。

**ATM取款场景因素与水平：**

| 因素 | 水平1 | 水平2 | 水平3 |
|------|-------|-------|-------|
| A：银行卡类型 | 本行卡 | 他行卡 | 无卡 |
| B：取款金额 | 100元 | 5000元 | 20000元 |
| C：密码输入 | 正确 | 错误1次 | 错误3次 |
| D：账户余额 | 充足 | 刚好等于取款额 | 不足 |

### ATM取款场景流程图

```

  │
  ▼

  ▼

  │
  ▼

  │
```

## 第04课时：Bug报告撰写

### 知识点回顾

高质量Bug报告包含以下要素：
- **摘要（Summary）**：简明描述问题
- **复现步骤（Steps to Reproduce）**：逐步操作描述
- **预期结果（Expected Result）**：系统应有的正确行为
- **实际结果（Actual Result）**：系统实际表现
- **严重程度（Severity）**：致命/严重/一般/轻微
- **优先级（Priority）**：紧急/高/中/低
- **环境信息**：操作系统、浏览器、版本号等

## 第05课时：ShopTest v1 测试计划与测试报告

### 知识点回顾

测试计划核心要素：测试目标、测试范围、测试策略、资源分配、进度安排、风险评估。
测试报告核心要素：测试概述、测试结果统计、Bug分析、质量评估、测试结论与建议。

---

### 参考答案：ShopTest v1 测试计划

#### 1. 项目概述

| 项目 | 内容 |
|------|------|
| **项目名称** | ShopTest v1.0 电商平台 |
| **项目背景** | 为电商业务提供商品浏览、购物车、订单管理、支付等核心功能 |
| **测试版本** | ShopTest v1.0 Build 20240301 |
| **测试负责人** | 测试组 |
| **测试周期** | 2024年3月4日 - 2024年3月15日（共10个工作日） |

#### 2. 测试目标

1. 验证系统功能是否符合需求规格说明书的要求
2. 发现并跟踪系统中的缺陷，确保上线前致命/严重Bug修复率达到100%
3. 验证系统在主流浏览器和移动设备上的兼容性
4. 评估系统性能是否满足设计要求（并发1000用户，响应时间<3秒）

#### 3. 测试范围

**包含范围（In Scope）：**
- 用户注册/登录模块
- 商品搜索与浏览模块
- 购物车模块
- 订单创建与管理模块
- 支付模块（模拟支付）
- 个人中心模块
- 后台商品管理模块

**不包含范围（Out of Scope）：**
- 第三方支付接口的真实交易测试
- 物流系统对接测试
- 推荐算法精准度测试

#### 4. 测试策略

| 测试类型 | 测试内容 | 工具/方法 | 负责人 |
|----------|----------|-----------|--------|
| 功能测试 | 各模块功能验证 | 等价类、边界值、场景法 | 测试组 |
| 接口测试 | API接口验证 | Postman + Newman | 测试组 |
| 性能测试 | 负载测试、压力测试 | JMeter | 测试组 |
| 兼容性测试 | 浏览器/设备兼容 | BrowserStack | 测试组 |
| 安全测试 | SQL注入、XSS、越权 | 手工+OWASP ZAP | 测试组 |

#### 5. 测试环境

| 环境 | 配置 |
|------|------|
| **操作系统** | 服务端：CentOS 7.9；客户端：Windows 11 / macOS 14 / iOS 17 / Android 14 |

| **数据库** | MySQL 8.0 |

#### 6. 进度安排

| 阶段 | 时间 | 工作内容 | 交付物 |
|------|------|----------|--------|
| 需求评审 | 3月4日 | 参与需求评审，理解功能点 | 评审记录 |

#### 7. 风险评估

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 需求变更频繁 | 测试用例返工，进度延期 | 中 | 需求冻结机制，变更需评审 |
| 测试环境不稳定 | 测试执行受阻 | 中 | 提前准备备用环境 |
| Bug数量超出预期 | 回归测试时间不足 | 高 | 预留缓冲时间，优先验证致命/严重Bug |
| 人员不足 | 测试覆盖不全面 | 低 | 提前协调资源，必要时申请增援 |

#### 8. 通过/失败标准

**通过标准：**
- 致命/严重Bug修复率100%，一般Bug修复率≥90%
- 功能测试用例执行率100%，通过率≥95%
- 性能指标满足设计要求

## 第06课时：HTTP请求与响应分析

### 知识点回顾

HTTP请求由请求行、请求头、请求体组成；HTTP响应由状态行、响应头、响应体组成。常见状态码：
- 2xx：成功（200 OK、201 Created）
- 3xx：重定向（301 Moved Permanently、302 Found、304 Not Modified）
- 4xx：客户端错误（400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、405 Method Not Allowed）
- 5xx：服务端错误（500 Internal Server Error、502 Bad Gateway、503 Service Unavailable）

### 参考答案：HTTP请求/响应分析练习

---

#### 练习1：分析以下HTTP请求

```
POST /api/login HTTP/1.1
Host: www.shoptest.com
Content-Type: application/json
Content-Length: 56
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: application/json

{"username":"alice","password":"abc123"}
```

**参考答案：**

| 字段 | 值 | 说明 |
|------|-----|------|
| 请求方法 | POST | 用于提交数据 |
| 请求路径 | /api/login | 登录接口地址 |
| HTTP版本 | HTTP/1.1 | 协议版本 |
| Host | www.shoptest.com | 目标服务器域名 |
| Content-Type | application/json | 请求体数据格式为JSON |
| Content-Length | 56 | 请求体字节长度 |
| User-Agent | Mozilla/5.0 (Windows NT 10.0; Win64; x64) | 客户端浏览器标识 |
| Accept | application/json | 客户端期望接收JSON格式响应 |
| 请求体 | `{"username":"alice","password":"abc123"}` | 登录凭证（JSON格式） |

#### 练习3：根据场景判断状态码

| 场景描述 | 状态码 | 说明 |
|----------|--------|------|
| 请求的资源不存在 | 404 Not Found | 服务器找不到请求的资源 |
| 用户未登录访问需要认证的接口 | 401 Unauthorized | 缺少有效的身份验证凭证 |
| 用户已登录但无权限访问该资源 | 403 Forbidden | 服务器拒绝执行请求 |
| 请求参数格式错误（如JSON语法错误） | 400 Bad Request | 客户端请求语法错误 |
| 服务器内部代码异常 | 500 Internal Server Error | 服务器内部错误 |
| 服务器维护中，暂时不可用 | 503 Service Unavailable | 服务暂时不可用 |
| 请求的资源已被永久移动到新URL | 301 Moved Permanently | 永久重定向 |
| 请求方法不被允许（如对只读资源使用POST） | 405 Method Not Allowed | 请求方法不被允许 |
| 网关/代理服务器从上游收到无效响应 | 502 Bad Gateway | 网关错误 |
| 资源未修改，可使用缓存版本 | 304 Not Modified | 协商缓存命中 |

#### 练习4：分析以下请求的问题

```
GET /api/user/delete?id=10001 HTTP/1.1
Host: www.shoptest.com
```

**参考答案：**

| 问题 | 说明 | 正确做法 |
|------|------|----------|
| 使用GET方法执行删除操作 | GET是安全且幂等的，不应有副作用 | 应使用DELETE或POST方法 |
| 敏感操作通过URL参数传递 | URL参数会记录在日志和浏览器历史中 | 应通过请求体或Header传递 |
| 缺少身份验证信息 | 无Token/Cookie，任何人可调用 | 应在Header中携带Authorization |
| 缺少CSRF防护 | 无CSRF Token，存在跨站请求伪造风险 | 应增加CSRF Token验证 |

**参考答案：**

```bash
#!/bin/bash
# 文件名: analyze_status_code.sh
# 功能: 统计访问日志中各HTTP状态码出现次数
# 用法: ./analyze_status_code.sh access.log

LOG_FILE="${1:-access.log}"

if [ ! -f "$LOG_FILE" ]; then
    echo "错误: 日志文件 $LOG_FILE 不存在"
    exit 1
fi

echo "=== HTTP状态码统计 ==="
echo "状态码 | 出现次数 | 占比"
echo "-------|----------|------"

TOTAL=$(wc -l < "$LOG_FILE")

awk '{print $9}' "$LOG_FILE" | \
    grep -E '^[0-9]{3}$' | \
    sort | uniq -c | sort -rn | \
    while read count code; do
        percent=$(echo "scale=2; $count * 100 / $TOTAL" | bc)
        printf "  %s   |   %5d   | %s%%\n" "$code" "$count" "$percent"
    done

echo "-------|----------|------"
echo "总计: $TOTAL 条记录"
```

#### 练习2：批量处理——将目录下所有.jpg图片重命名为"日期_序号"格式

**需求：** 将`/data/images/`目录下所有`.jpg`文件重命名为`20240315_001.jpg`格式。

**参考答案：**

```bash
#!/bin/bash
# 文件名: batch_rename.sh
# 功能: 批量重命名图片文件
# 用法: ./batch_rename.sh /data/images

TARGET_DIR="${1:-.}"
DATE=$(date +%Y%m%d)
COUNTER=1

if [ ! -d "$TARGET_DIR" ]; then
    echo "错误: 目录 $TARGET_DIR 不存在"
    exit 1
fi

# 切换到目标目录
cd "$TARGET_DIR" || exit 1

# 统计待处理文件数量
TOTAL=$(ls -1 *.jpg 2>/dev/null | wc -l)
if [ "$TOTAL" -eq 0 ]; then
    echo "未找到 .jpg 文件"
    exit 0
fi

echo "找到 $TOTAL 个 .jpg 文件，开始重命名..."

for file in *.jpg; do
    # 生成序号（3位补零）
    SEQ=$(printf "%03d" $COUNTER)
    NEW_NAME="${DATE}_${SEQ}.jpg"
    
    # 避免覆盖已有文件
    if [ -f "$NEW_NAME" ]; then
        echo "警告: $NEW_NAME 已存在，跳过"
        continue
    fi
    
    mv "$file" "$NEW_NAME"
    echo "重命名: $file -> $NEW_NAME"
    
    COUNTER=$((COUNTER + 1))
done

echo "重命名完成，共处理 $((COUNTER - 1)) 个文件"
```

#### 练习3：健康检查——检测Web服务是否正常运行

**需求：** 检测指定URL的HTTP状态码，若连续3次检测失败则发送告警邮件。

**参考答案：**

```bash
#!/bin/bash
#文件名: health_check.sh
#功能: Web服务健康检查
#用法: ./health_check.sh http://www.shoptest.com 3 3

URL="${1:-http://localhost:8080}"
INTERVAL="${2:-60}"        # 检测间隔（秒）
MAX_FAIL="${3:-3}"         # 最大连续失败次数
ALERT_EMAIL="admin@shoptest.com"
FAIL_COUNT=0
LOG_FILE="/var/log/health_check.log"

check_service() {
    HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" \
        --connect-timeout 5 --max-time 10 "$URL")
    
    if [ "$HTTP_CODE" -ge 200 ] && [ "$HTTP_CODE" -lt 400 ]; then
        echo "$HTTP_CODE"
        return 0
    else
        echo "$HTTP_CODE"
        return 1
    fi
}

send_alert() {
    local subject="[告警] 服务不可达: $URL"
    local body="服务 $URL 已连续 ${MAX_FAIL} 次检测失败。\n检测时间: $(date '+%Y-%m-%d %H:%M:%S')\n请尽快排查。"
    
    echo -e "$body" | mail -s "$subject" "$ALERT_EMAIL"
    echo "$(date '+%Y-%m-%d %H:%M:%S') | 已发送告警邮件至 $ALERT_EMAIL" >> "$LOG_FILE"
}

echo "=== 服务健康检查启动 ==="
echo "目标URL: $URL"
echo "检测间隔: ${INTERVAL}秒"
echo "最大连续失败次数: $MAX_FAIL"
echo "========================="

while true; do
    TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
    STATUS_CODE=$(check_service)
    
    if [ $? -eq 0 ]; then
        echo "$TIMESTAMP | HTTP $STATUS_CODE | 服务正常"
        echo "$TIMESTAMP | HTTP $STATUS_CODE | 服务正常" >> "$LOG_FILE"
        FAIL_COUNT=0
    else
        FAIL_COUNT=$((FAIL_COUNT + 1))
        echo "$TIMESTAMP | HTTP $STATUS_CODE | 服务异常 (连续失败: $FAIL_COUNT/$MAX_FAIL)"
        echo "$TIMESTAMP | HTTP $STATUS_CODE | 服务异常 (连续失败: $FAIL_COUNT/$MAX_FAIL)" >> "$LOG_FILE"
        
        if [ "$FAIL_COUNT" -ge "$MAX_FAIL" ]; then
            echo "$TIMESTAMP | 触发告警阈值！"
            send_alert
            FAIL_COUNT=0  # 重置计数，避免重复告警
        fi
    fi
    
    sleep "$INTERVAL"
done
```

**预期输出示例：**

```

=========================
2024-03-15 09:00:00 | HTTP 200 | 服务正常
2024-03-15 09:01:00 | HTTP 200 | 服务正常
2024-03-15 09:02:00 | HTTP 503 | 服务异常 (连续失败: 1/3)
2024-03-15 09:03:00 | HTTP 503 | 服务异常 (连续失败: 2/3)
2024-03-15 09:04:00 | HTTP 503 | 服务异常 (连续失败: 3/3)
2024-03-15 09:04:00 | 触发告警阈值！
2024-03-15 09:05:00 | HTTP 200 | 服务正常
```

#### 查询5：验证热销商品排行榜数据准确性

**场景：** 验证销量前5的商品排行是否与实际订单数据一致。

```sql
SELECT 
    p.product_id,
    p.name,
    SUM(oi.quantity) AS total_sold,
    SUM(oi.quantity * oi.price) AS total_revenue
FROM products p
JOIN order_items oi ON p.product_id = oi.product_id
JOIN orders o ON oi.order_id = o.order_id
WHERE o.status = 'paid'
GROUP BY p.product_id, p.name
ORDER BY total_sold DESC
LIMIT 5;
```

**预期结果：**

| product_id | name | total_sold | total_revenue |
|------------|------|------------|---------------|
| 101 | 无线鼠标 | 356 | 31994.40 |
| 205 | 机械键盘 | 289 | 86491.00 |
| 103 | 蓝牙耳机 | 234 | 46786.66 |
| 312 | 手机支架 | 198 | 3950.10 |
| 156 | USB-C数据线 | 175 | 2625.00 |

**验证要点：**
- 仅统计`status='paid'`的订单（排除未支付/已取消订单）
- `total_sold`为该商品在所有已支付订单中的累计销量
- `total_revenue`为累计销售额
- 排序与前端展示的热销榜一致
